In September 2026 I migrated the Apache Superset fork behind Datakimia's embedded analytics platform from 4.1 to 6.1: three major versions, six upstream merges and about 4,400 files touched in the last one, in 30 calendar days. An AI agent resolved most of the merge conflicts. What kept the upgrade safe was not the AI. It was a set of boring, deterministic checks that caught three features the merge had silently broken.

This is the playbook, including what went wrong.

The starting point

The platform serves analytics to several customers. Each customer runs its own Superset instance, embedded in a Next.js portal with guest tokens and row-level security. Over two years the fork had accumulated around 430 custom commits (roughly 80 files and 6,000 lines of product code): custom SSO, saved filter sets, a calendar date picker, cache handling for embedded guests, structured logging for Google Cloud, and several security patches.

Staying on 4.1 was no longer an option:

  • Upstream support had moved to the 6.x line, and 4.1.1 had known CVEs.
  • In embedded mode, 4.1.1 returned generated SQL to guest users.
  • 6.1 ships MCP (Model Context Protocol) support, which the product roadmap needed for AI over BI.

And the constraints made it risky:

  • One Superset per customer. Every upgrade step multiplies by the number of tenants: metadata upgrades, config diffs and cut-over windows.
  • The metadata database cannot be downgraded. Rollback means restoring a snapshot.
  • Embedding has to keep working at every step: guest tokens, RLS, SSO.

Step 1: Inventory the fork before touching it

The first deliverable was not code. It was a list of every custom change against the 4.1.1 tag (git diff 4.1.1...fork), each one classified as:

  • Carry — port it as is.
  • Replace — upstream now offers config, theming or an extension point that does the same job.
  • Drop — remove it, or make an explicit product decision.

Next to it, I read the upstream changelogs for the whole range and flagged breaking changes by product area. Two of them shaped the plan: 6.0 replaces the SQL parser with SQLGlot, which can change the SQL generated under RLS, and 6.0 moves the frontend to a new theming system that breaks old theme tokens.

Step 2: A security gate before the migration

Before any major jump, I closed the known risks on the current line:

  • Merged the 4.1.2, 4.1.3 and 4.1.4 patch releases, one merge per tag.
  • Upgraded jspdf to a version without the published CVEs.
  • Wrote automated tests for cache isolation between embedded guests: the cache key now includes the user, the resources and the RLS rules from the guest token, so two customers can never share a cached chart.

The point of this gate: the most important invariant of a multi-tenant BI product (no data leaking between customers) gets a test before the risky change, not after.

Step 3: One merge per upstream tag, with a waypoint

Instead of jumping from 4.1 to 6.1 in one merge, I went through 5.0 as a waypoint in a non-production environment, then 6.0, then 6.1. Six upstream merges in total. Each merge kept the conflicts small enough to understand and attribute.

Before each merge I wrote down the rule for resolving it. For 6.1 it was: keep our configuration, the date-only filters for public users, the chart-data cache and the thumbnail capture; take the 6.1 tree for everything else. That sentence went into the merge commit message, so anyone reading the history knows what was intentional.

Step 4: Let the AI merge, and verify what it cannot see

I used Cursor to resolve the bulk of the conflicts and adapt code to the new APIs. That is where AI shines: thousands of mechanical changes across a large codebase. It is also where it fails silently.

After the 5.0 merge everything built, the app started, and three features were gone:

  • The saved filter sets API returned 404, because its registration had been dropped.
  • The "save filters" buttons disappeared, because a feature flag was lost.
  • Request IDs stopped appearing in the Google Cloud logs, because the tracking hook was no longer installed.

The files were all still there. Nobody was calling them. This is the typical result of resolving a shared file with "take theirs": the module survives, its wiring does not.

So I wrote a wiring check: a shell script with 23 assertions that each custom feature is still used, not just present. It also lists the files that must never be resolved with "take theirs" (the filter bar, the time filter plugin, the app entry point, the feature flags, the Superset config). If a new silent disconnection is ever found, its assertion is added in the same change.

A second script scans for 4.x patterns that break in 6.x: old theme tokens, removed component shims, renamed icons, deprecated props.

Both scripts, plus a production-equivalent build, run before every push. That rule lives in the agent's own instructions, so the AI has to pass the checks before it can push anything. The AI does the work; deterministic checks decide if it is done.

Step 5: Smoke tests in phases, with a stop rule

Every environment runs the same smoke test: 5 phases and 17 steps, in order, stopping at the first critical failure.

  1. Infrastructure — image build, startup, database migrations, health check.
  2. Auth and embedding (critical) — OAuth with each identity provider, dashboard loaded with a guest token, cache hit.
  3. Product (critical) — time filters, saved filter sets, native filters, cross-filtering.
  4. Export and thumbnails — PDF export, dashboard thumbnails.
  5. SQL and data — async SQL Lab, BigQuery exploration.

The environments form a ladder: local Docker, then an ephemeral environment per branch on Kubernetes, then a pilot customer, then pre-production with a copy of production metadata, then production customer by customer. Rollback is a rehearsed snapshot restore, because a metadata downgrade is not an option.

Results

  • Three major versions (4.1 → 5.0 → 6.0 → 6.1) and six upstream merges in 30 calendar days.
  • About 100 hours of work.
  • Three silent regressions caught by automated checks before reaching any customer.
  • Security debt closed first, with tenant isolation covered by tests.
  • MCP available on the new version for the product's AI features.

As of October 2026, 6.1 runs in the ephemeral and pre-production environments, and production customers move to it one at a time, pilot first.

The playbook

If you maintain a fork of an open source project and need to catch up with upstream:

  1. Inventory the fork against its base tag and classify every change as carry, replace or drop.
  2. Read the upstream changelogs for the whole range and flag breaking changes by area.
  3. Close security patches on your current line first, and test your critical invariants (security, tenancy) before the jump.
  4. Merge one upstream tag at a time. Write the resolution rule in the merge commit.
  5. Keep a list of files that are always merged by hand.
  6. Write a script that verifies each custom feature is still wired in, not just present.
  7. Scan automatically for patterns the new version removed.
  8. Run the same build as CI locally before every push.
  9. Climb an environment ladder with phased smoke tests and a stop rule; roll out tenant by tenant.
  10. If an AI agent does the merging, put all of the above in its instructions, so it works inside the checks instead of around them.
