The Problem: Unit Tests Don't Catch Everything

Your unit tests pass. Your integration tests pass. You deploy. Then a customer reports: "The checkout button doesn't work." But it works in your tests. Why?

Because unit tests test code in isolation. They don't test:

  • Real user flows: JavaScript not loading, CSS broken, form submission failing silently
  • Cross-browser issues: Works in Chrome, breaks in Safari
  • Race conditions: Timing issues between frontend and backend
  • External integrations: Stripe, payment gateways, third-party APIs
  • Mobile behavior: Touch events, responsive design, mobile-specific bugs

That's what E2E tests are for.

What E2E Testing Does

Real Browser Automation

Playwright launches a real browser (Chrome, Firefox, Safari) and simulates a user. Clicks buttons, fills forms, waits for data, checks results. If it breaks in the real browser, the test fails.

Multi-browser Coverage

Test Chrome, Firefox, Safari, Edge. Catch cross-browser bugs before customers do.

Mobile Testing

Emulate iPhone, Android. Test touch gestures, viewport sizes, mobile-specific bugs.

CI Integration

Tests run on every deployment. Slow (15-30 minutes for full suite), but you catch issues before production.

How We Build It

Week 1-2: Audit & Strategy

  • Identify critical flows: What breaks your business? Checkout, payments, signup, core features.
  • Decide scope: Test Chrome only (faster) or multi-browser? Desktop only or mobile too?
  • Set up Playwright: Modern tooling, page objects, test helpers, visual regression testing.

Week 3-5: Build Tests

  • Core flows first: Signup → Login → Use feature → Checkout → Success
  • Error paths: Invalid input, network failures, timeouts, user cancels payment
  • Edge cases: Slow network, expired sessions, concurrent operations
  • Visual regression: Screenshots of each page. Detects unintended design changes.

Week 6-8: CI Setup & Handoff

  • Integrate into CI: GitHub Actions, GitLab CI, or your pipeline
  • Parallel execution: Run 10+ tests at once. Full suite in 15-30 minutes.
  • Team training: How to write tests, debug failures, maintain suite

Playwright vs Cypress

Playwright (Our recommendation)

  • Multi-browser: Chrome, Firefox, Safari, Edge with one codebase
  • Faster: Parallel execution, better performance
  • Mobile support: Emulate iOS and Android devices
  • Better debugging: Video recording, HAR files, detailed traces

Cypress

  • Developer experience: Easier learning curve, great UI for running tests
  • Limitations: Chrome only (until recently), slower CI

FAQ

How many tests do we need?

For a typical SaaS: 20-50 tests covering critical flows. For e-commerce with checkout: 50-100+ tests. Focus on high-risk flows (payments, signup, core features). Low-risk UI can be tested manually or with visual regression.

Are E2E tests slow?

Yes, compared to unit tests. A full suite takes 15-30 minutes. But they run in parallel in CI, so you don't wait. And they run overnight, not during your day.

Do E2E tests replace unit tests?

No. Unit tests are fast and catch bugs early. E2E tests catch integration and UI bugs. You need both.

What about flaky tests?

Flaky tests (sometimes pass, sometimes fail) are a real problem. We build with explicit waits, avoid sleep(), and design tests to be deterministic. But some flakiness is inevitable—we mitigate with retries and clear logging.

Can we test payments without hitting production?

Yes. Stripe, PayPal, and other gateways have test modes. We use test card numbers and test API keys. Real transactions, fake money.

What about visual regression?

Playwright can take screenshots after each flow and compare them. Detects unintended CSS changes, design regressions, layout breaks. Useful for catching "oops, I changed the wrong color" bugs.
